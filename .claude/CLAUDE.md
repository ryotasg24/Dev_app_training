# CLAUDE.md（筋力トレーニング記録アプリ）

このファイルには、このプロジェクトだけのルールを書きます。回答の言語や文字化け対策など、すべてのプロジェクトに共通するルールは、上位フォルダの `C:\dev\.claude\CLAUDE.md` に書いてあります。

## プロジェクト概要

- **何を作るか**：自宅での筋トレとストレッチを、iPhoneで手早く記録するPWA（ホーム画面に追加して使うWebアプリ）。個人で使う。
- **主な機能**：セッションの記録（開始・終了ボタン、手入力）、人体図で回復状況を表示、消費カロリーの推定、カレンダー、グラフ、ショートカット経由でヘルスケアに送る、JSONでのバックアップと復元。
- **端末**：主にiPhone（Safariからホーム画面に追加して使う）。PC・iPadの画面幅にも対応する。
- **サーバーなし**：データは端末内のIndexedDBにだけ保存する。ログイン機能やAPIサーバーはない。
- **公開先**：GitHub Pages（https://ryotasg24.github.io/Dev_app_training/ ）。mainブランチにpushすると、GitHub Actionsで自動公開する。
- **進み具合**：要件定義（第2.5版）・基本設計（第1.3版）・デザイン仕様書（第1.1版）が完了。全14画面（メニューの選択を含む）、人体図、アイコン、メニュー方式の計測、たんぱく質の目安を実装し、GitHub Pagesに公開中。データ形式は版3。未決はアプリの名前のみ（仮：「筋トレ記録」）。
- **素材**：人体図は react-native-body-highlighter（MIT）、アイコンは Tabler Icons（MIT）。素材を追加するときは、公開リポジトリで再配布できるライセンスか確認し、`public/third-party-licenses.txt` に追記する。

### 技術構成

TypeScript、React、Vite、vite-plugin-pwa、Dexie.js（IndexedDB）、Chart.js、date-fns、Vitest。画面の切り替えはReact Routerのハッシュ方式（`#/calendar`）を使う。

### フォルダ構成（予定。詳しくは基本設計書 2.3）

```
src/
  ui/        共通の部品（ボタン、レイアウト、人体図など）
  features/  画面ごとの部品と処理（home、session、calendar、stats、settings など）
  domain/    計算ロジック（カロリー、回復、日付、集計）。React・Dexieに依存しない
  db/        Dexieの定義、データの読み書き、移行、バックアップと復元
  platform/  端末の機能（ショートカットの起動、ファイルの共有、永続ストレージ）
仕様書/      要件定義書、基本設計書など
```

## よく使うコマンド

`package.json` に次のスクリプトを用意してある。

| コマンド | 内容 |
|---|---|
| `npm install` | 必要な部品をインストールする |
| `npm run dev` | 開発用サーバーを起動する（PCのブラウザで確認する） |
| `npm run build` | 公開用にビルドする（`dist/` に出力） |
| `npm run preview` | ビルドした結果を確認する（PWAとオフラインの動作は、これで確認する） |
| `npm test` | 単体テストを実行する（Vitest） |
| `npm run typecheck` | 型チェックを行う（`tsc --noEmit`） |
| `npm run lint` | コードの書き方をチェックする（ESLint） |

コミットの前に、`npm run typecheck` と `npm test` が通ることを確認する。

## コーディングルール

### 名前の付け方

| 対象 | 書き方 | 例 |
|---|---|---|
| 関数・変数 | 英語、キャメルケース | `calcCalories`、`recoveryHours` |
| Reactのコンポーネント、型、インターフェース | 英語、パスカルケース | `BodyMap`、`Session` |
| 定数 | 英語、大文字のスネークケース | `DEFAULT_FORGOT_END_HOURS` |
| コンポーネントのファイル | パスカルケース | `BodyMap.tsx`、`BodyMap.module.css` |
| それ以外のファイル | キャメルケース | `calories.ts`、`calories.test.ts` |
| 真偽値 | `is`、`has`、`can` で始める | `isPreset`、`hasSoreness` |

- 名前に日本語やローマ字（`kinniku` など）は使わない。

### コメント・文章
- コメントは**日本語**で書く。「何をしているか」より「なぜそうしているか」を書く。
- 関数には、目的・引数・戻り値を説明するJSDocコメント（`/** */`）を日本語で付ける。計算式には、根拠になる要件のIDを書く。
- 画面に表示する文言は日本語にする。
- コミットメッセージは日本語で書く。

### TypeScript・React
- `tsconfig` の `strict` を有効にする。`any` は使わず、どうしても必要なときは理由をコメントに書く。
- コンポーネントは関数で作り、Hooksを使う。クラスのコンポーネントは使わない。
- 押せる部品はHTMLの `button`・`a` 要素で作る（キーボードで操作できるようにするため）。`div` に `onClick` を付けない。
- スタイルはCSS Modulesで書き、色や余白はCSS変数を使う（ダークモードに対応するため）。

### 設計上の決まり（基本設計書より）
- **計算ロジックは `domain/` に置く**。domainの関数はReactにもDexieにも依存させず、現在時刻は `Date.now()` を中で呼ばずに引数で受け取る（テストできるようにするため）。
- **データベースの読み書きは `db/` だけで行う**。画面から直接Dexieを操作しない。
- 時刻は**エポックミリ秒（数値）**で保存する。日付は端末の時間帯での `YYYY-MM-DD` 文字列にする。セッションの日付は**開始時刻の日付**で決める。
- データには `id`（UUID）、`createdAt`、`updatedAt`、`deleted` を持たせる。削除は印を付けるだけで、データは消さない。
- 複数のテーブルを変える処理は、1つのトランザクションで行う。
- IndexedDBのデータベース名には接頭辞 `dat-` を付ける。localStorageは使わない。
- データ形式を変えたら、Dexieの版を上げて移行処理を書き、その移行のテストも書く。

### テスト
- `domain/` の関数には、必ずVitestの単体テストを書く。テストファイルは対象と同じフォルダに `○○.test.ts` として置く。
- テスト名は日本語で書く（例：`it('日をまたぐセッションは開始日の記録になる', ...)`）。
- 境界になる値（日付の変わり目、回復目安の50%ちょうど、0分・1分未満など）をテストする。

## 注意事項

### 秘密情報
- `.env` と `.env.*` は**絶対にGitにコミットしない**（`.gitignore` で除外済み。例として見せるための `.env.example` だけはコミットしてよい）。
- APIキー、トークン、パスワードを**コードに直接書かない**。必要になった場合は環境変数から読み込み、先にユーザーに相談する。
- このアプリはサーバーを持たないため、ビルドした結果はすべて公開される。ビルドに含まれる値（`VITE_` で始まる環境変数を含む）には、秘密情報を入れない。

### データとプライバシー
- 記録したデータを外部に送信する処理を作らない。外部の解析ツール、広告、外部フォント、CDNから読み込むスクリプトは組み込まない。
- 外部への通信は、GitHub Pagesからアプリを読み込むことと、更新の確認だけにする。

### 公開まわり
- GitHubのリポジトリ名（`Dev_app_training`）を変えない。アプリのURLが変わり、ホーム画面に追加したアプリとデータが使えなくなる。
- Viteの `base` は `/Dev_app_training/` にする。

### ファイル
- テキストファイルはUTF-8（BOMなし）、改行コードはLFにする（`.gitattributes` で設定済み）。例外として、アプリが書き出すCSVファイルだけは、Excelで文字化けしないようBOMを付ける。
- `node_modules/`、`dist/`、`dev-dist/`、`coverage/` はコミットしない（`.gitignore` で除外済み）。

### Git
- このリポジトリでは、作業のまとまりごとに**確認なしでコミットし、mainへpushしてよい**（ユーザーの許可済み）。判断の要らない作業は、指示を待たずに進めてよい。
- ただし、影響の大きい変更は、**事前にユーザーに確認する**。例：データ形式（IndexedDBのテーブル定義）の変更、既存のデータを消したり書き換えたりする処理、公開URLやリポジトリの設定、部品の大きな版の更新、仕様書の内容と違う作り方。
- mainにpushすると自動で公開されるため、pushの前に `npm run typecheck`、`npm test`、`npm run build` が通ることを確認する。
