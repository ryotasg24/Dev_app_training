# デザイン仕様書の作成・改訂

画面の見た目と動きのルールを決める文書です。色などの値はCSS変数にまとめ、画面側では直接色を書かない前提で書きます。
要件は要件定義書（skill：`requirements-doc`）、画面の項目や遷移は基本設計書（skill：`basic-design-doc`）に書きます。

ひな形：[template.md](template.md)

---

## 1. 利用者の好み（デザインの指向）

- **洗練された、スタイリッシュなデザイン**を好む。派手さより、落ち着いた配色・ていねいな余白・なめらかな動きで質を出す。
- 色は「状態を表すもの」と「押せるもの」にだけ使い、ほかは控えめにする。
- **動きは参考記事のルール**に従う（「4. 動きのルール」）。
- グラフは、推移を**マーカー付きの折れ線グラフ（データラベル付き）**で見せるのを好む。
- 決めかねる見た目は、**言葉だけでなくプレビュー画像**を作って選んでもらう（例：アイコン案を4つ並べた画像、人体図の色付けの見本）。

---

## 2. 進め方（必ずこの順で）

### 手順1：材料を集める
- 要件定義書と基本設計書を読み、画面・部品・状態の種類を洗い出す。
- 既存のデザイン仕様書を改訂する場合は、先に全体を読み、版数・未決の項目を確認する。

### 手順2：作る前に質問する
- 判断が必要な点（メインの色、素材、アイコンの絵柄、アプリの名前など）は、まとめて質問する。選択肢と推奨案を付ける。
- 見た目の選択肢は、ブラウザで描画した**プレビュー画像**を作業用フォルダに保存し、その場所を質問の中に書く。
- 利用者が色や素材を指定した場合は、それを採用したうえで、問題（読みにくさ、ライセンス）があれば解決策をセットで示す。

### 手順3：事実を確認してから決める
- **素材のライセンス**を必ず確かめる（「5. 素材の選び方」）。
- 色の組み合わせは**コントラスト比**を確かめる（本文4.5:1以上、大きな文字とアイコン3:1以上）。
- 実装後は、**実際のブラウザで画面を撮影**して確かめる。スマホ縦向き・横向き、幅320px、PC、ライトモードとダークモードを対象にする。アニメーションは途中の状態も撮影する。

### 手順4：書く
[template.md](template.md) の章立てに沿って書く。

### 手順5：整合を保つ
- 基本設計書の画面の項目・レイアウトの条件・部位IDなどとそろえる。
- 素材を決めたら、要件定義書の未決事項も「決定済み」にする。
- プロジェクトの CLAUDE.md（素材のライセンス、進み具合）を更新する。
- 版数を上げ、変更履歴に「何を、なぜ」を書く。

## 3. 書き方と決め方

### 色
- すべての色を**CSS変数**で定義し、ライトとダークの値を表にする（例：`--color-primary`）。
- 利用者が指定した色が淡すぎる・濃すぎる場合は、用途を分ける。
  - 例：淡緑色 `#CEE6C1` をメインの色にしたときは、白い文字が読めない（約1.3:1）ため、塗りの上の文字は濃い緑 `#1F3A14`、白い背景の上の文字・線は濃い緑 `#3F6B2A` を別の変数（`--color-on-primary`、`--color-primary-strong`）にした。
- 状態の色（例：疲労中・回復中・回復済み）は、色だけに頼らず、凡例と文字を合わせて使う。

### 文字・余白・部品
- 文字の大きさは用途ごとの表にする。動く数字は等幅数字にする。**入力欄は16px以上**（iPhoneで入力時に拡大されないように）。
- 余白は4の倍数だけを使う。押せる部分は44px四方以上にする。
- 部品は「部品・見た目・使う場所」の表にする。押せる部品は、押したときの反応（少し縮める）とキーボード操作時の枠を決める。

### 画面
- 主な画面は、文字の図（ワイヤーフレーム）で配置を示す。スマホとPCで配置が変わる画面は両方を書く。

## 4. 動きのルール（参考：https://photoshopvip.net/152964 ）

「心地よいWeb遷移アニメーションの基本ルール6個」に沿って決める。

| ルール | 決め方 |
|---|---|
| フェード | 画面の切り替えは、動きとフェード（不透明度0→100%）を組み合わせる |
| 拡大 | 手前の層として現れる画面は、少し拡大しながら（例：96%→100%）現れる |
| 一貫した方向 | 階層の移動は横方向だけ（進む＝右から、戻る＝左から）。タブも並びの向きに合わせる。縦の動きは「手前の層」だけに使う。縦横を混ぜない |
| 速さ | 100〜500msの範囲にする。画面の切り替えは200〜320ms、ページ内の動き（ボタン・チップなど）は150〜200msと、ページ内を速くする |
| 段階的な表示 | 画面の中の要素は、上から順に少しずつ（例：40ms）遅らせて表示する |
| 空間 | 「詳しい画面は右の奥」「戻る先は左」「下から重なる層」のように、アプリの空間をそろえる |

- 動きの曲線は1つに統一する（例：`cubic-bezier(0.22, 1, 0.36, 1)`）。
- 端末の「視差効果を減らす」（`prefers-reduced-motion`）がオンのときは、動きを止める。
- 遷移の種類を決める処理は、普通の関数にして単体テストを書く。

## 5. 素材の選び方（画像・図・アイコン）

公開されるアプリに組み込んだ素材は、誰でも取り出せる。**ソースへの組み込みと公開（再配布）が認められているか**を、利用規約を読んで確かめてから使う。

| 確認すること | 判断の例 |
|---|---|
| 透かし（ウォーターマーク）や番号が入っていないか | ストックフォトの見本（例：Adobe Stockの透かし入り画像）は、購入しないと使えない |
| 素材そのものの再配布が禁止されていないか | 再配布禁止の素材（例：一部のピクトグラム素材サイト）は、公開リポジトリに置けない |
| ロゴ・アイコンとしての使用が禁止されていないか | デザインツールの素材（例：Canva）は、ロゴ・アプリのアイコンへの使用や、単体での配布が禁止されている |
| ライセンスの種類 | MIT・ISC などは、著作権表示を残せば組み込み・公開・改変ができる |

- 使えない場合は、理由を利用者に説明し、条件を満たす**代わりの候補**を、プレビュー画像つきで示す。
- 採用した素材は、出典・作者・ライセンスを仕様書に書き、ライセンス文をアプリと一緒に配信する（例：`public/third-party-licenses.txt`）。
- 素材のデータを変換して使う場合は、変換したファイルの先頭に出典を書き、「直接編集しない」と明記する。

## 6. 必ず検討する観点

| 観点 | 確認すること |
|---|---|
| 方針 | 片手で使えるか、状態がひと目でわかるか、端末になじむか |
| 色 | ライト・ダーク、コントラスト、状態の色と凡例 |
| 文字 | 大きさ、太さ、等幅数字、入力欄の大きさ |
| 部品 | ボタン・カード・お知らせ・チップ・入力欄・ダイアログ・タブの見た目と、押したときの反応 |
| レイアウト | スマホ縦・横、幅320px、PC。画面の端の余白、安全領域（ノッチ） |
| 図・素材 | ライセンス、部位などの対応表、色を付けない部分 |
| アイコン | アプリのアイコン（各サイズ、切り取られても欠けない余白）、画面内のアイコンの一覧 |
| グラフ | 種類、線・点・ラベル、軸、点が多いときの間引き、動き |
| 動き | 遷移の種類・時間・曲線、段階的な表示、動きを減らす設定 |
| アクセシビリティ | コントラスト、色以外の手がかり、読み上げ用の説明、文字の拡大 |

## 7. 具体例（筋トレ記録アプリ：`仕様書/デザイン仕様書.md`）

| 場面 | 起きたこと・決めたこと | 学んだこと |
|---|---|---|
| メインの色 | 利用者が淡緑色 `#CEE6C1` を指定 | 指定を採用し、文字・線用の濃い緑を別の変数にして読みやすさを保った |
| 人体図の素材 | 提示された画像は透かし入りの有料素材、ピクトグラム素材は再配布禁止だった | 理由を説明し、MITの react-native-body-highlighter を、色付けのプレビュー画像つきで提案して採用した |
| アイコン | Canvaの素材は規約上使えなかった | Tabler Icons（MIT）から4案のプレビュー画像を作り、バーベルを選んでもらった |
| 部位の対応 | 素材に腸腰筋がなかった | 素材の部位名と自分の部位IDの対応表を作り、足りない部位の扱いを質問して決めた |
| グラフ | 棒グラフから、マーカー付きの折れ線（データラベル付き）に変更 | 0の点にはラベルを出さない、週は7日分すべての日付を出す、など読みやすさの細部まで決める |
| 画面遷移 | 参考記事の6つのルールに沿って、進む・戻る・タブ・シート・フェードの5種類を決めた | 種類・方向・時間を表にし、ダークモードと途中の状態まで撮影して確かめた |
