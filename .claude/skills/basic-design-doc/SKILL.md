# 基本設計書の作成・改訂

要件定義書で決めた「何を作るか」を、「どう作るか」に落とし込む文書です。実装を始めるときに迷わない状態にすることが目的です。
要件は要件定義書（skill：`requirements-doc`）、見た目はデザイン仕様書（skill：`design-spec-doc`）に書きます。

ひな形：[template.md](template.md)

---

## 1. 進め方（必ずこの順で）

### 手順1：要件定義書を読む
- 要件定義書の全体を読み、要件ID・優先度・制約・未決事項を把握する。
- 既存の基本設計書を改訂する場合は、先に全体を読み、版数・変更履歴・残っている課題を確認する。

### 手順2：作る前に質問する
設計を左右する判断（例：フレームワーク、レイアウトの切り替え条件、外部連携の方式）は、書き始める前に**まとめて質問**する。
- 各質問に選択肢を2〜4個付け、勧める案を先頭に「（推奨）」と書き、利点・欠点を1行で添える。
- 要件定義書の未決事項のうち、設計で決めるものは、ここで質問して決める。
- 慣例で決められること（例：日付ライブラリ、テストの道具）は質問せずに決め、報告で理由を伝える。

### 手順3：事実を確認してから決める
- **外部連携**（OSの機能、別アプリとの受け渡し）は、公式情報や実機で確かめる。確かめられない部分は「残っている課題」に入れ、確認の方法と時期を書く。
- **部品（ライブラリ）**は、ライセンスと最新の版を確かめる（例：`npm view <名前> version license`）。
- **計算例**は、実際に計算して確かめる（四捨五入の結果まで）。実装後は、同じ例を単体テストにする。

### 手順4：書く
[template.md](template.md) の章立てに沿って書く。設計の原則は「2. 設計の原則」、書き方は「3. 書き方」を守る。

### 手順5：整合を保つ
- 設計で要件の変更が必要になったら、**先にユーザーに相談**し、了承を得てから要件定義書も直す。
- 要件定義書の未決事項に答えたら、要件定義書の未決事項の表も「決定済み」にする。
- デザイン仕様書と重なる箇所（画面の項目、レイアウトの条件、部位IDなど）をそろえる。
- プロジェクトの CLAUDE.md（技術構成、フォルダ構成、設計上の決まり、進み具合）を更新する。
- 版数を上げ、変更履歴に「何を、なぜ」を1行で書く。

### 手順6：報告する
- 作った章の一覧と、**確認してほしい設計判断**を番号つきで示す。
- 自分で決めた値（例：強度ごとのMETs）は、仮定として明示する。

## 2. 設計の原則

| 原則 | 内容 |
|---|---|
| 計算と画面を分ける | 計算ロジックは、画面にもデータベースにも依存しない普通の関数にする（`domain` 層）。**現在時刻は中で取らず、引数で受け取る**（日付の境目をテストできるように） |
| 層を決める | 画面、計算ロジック、データ操作、端末機能のように層を分け、依存してよい向きを表で決める |
| データの共通の項目 | すべてのデータに一意のID、作成日時、更新日時、削除済みの印を持たせる。削除は印を付けるだけにする（将来の同期や復元のため） |
| 時刻の持ち方 | 時刻は数値（エポックミリ秒）で保存し、日付は端末の時間帯での `YYYY-MM-DD` で別に持つ |
| データ形式の版 | 保存する形を変えたら版を上げ、既存のデータを自動で移行する。版ごとの変更を表にし、移行には単体テストを書く。古いバックアップファイルにも同じ移行をかける |
| まとめて書き込む | 複数のテーブルを変える処理（終了して保存、復元など）は1つのトランザクションで行い、途中で失敗したら元に戻す |
| 二度押しに強くする | 状態を進める操作（例：「次の種目へ」）は、押したときの状態を渡し、すでに進んでいたら何もしない |
| 境目を設計する | 日付の変わり目、0時前後の初期値、0や上限の値、1分未満などを、設計の段階で決めておく |
| 公開と更新 | 公開先のURLの決まり、更新を利用者に知らせる方法、オフラインでの動作を決める |

## 3. 書き方

- **日本語**で、**平易な言葉**を使う。一文には1つのことだけを書く。専門用語には、初出でかっこ書きの説明を付ける。
- **表を中心に**し、流れは図（mermaid の flowchart）で示す。
- 技術を選ぶときは「分類・採用する技術・選んだ理由」の表にする。
- 画面は「No・画面・URL・主な内容」の一覧と、画面ごとの「項目・内容」の表で書く。関係する要件IDを添える。
- 計算は、式・使う値・端数の処理・**具体的な計算例**をセットで書く。
- 外部連携は、**実機で確かめたこと**と**間違えやすかった点**を、日付つきで残す。
- 要件定義書の未決事項への回答を、章を立てて表にする。

## 4. 必ず検討する観点

| 観点 | 確認すること |
|---|---|
| 技術構成 | フレームワーク、ビルド、保存方式、テスト、公開方法と、選んだ理由。ライセンス |
| 画面の切り替え | 公開先で再読み込みしても壊れない方式か（例：GitHub Pages ではハッシュ方式） |
| 画面 | 一覧、遷移図、各画面の項目、入力チェック、メニューを隠す画面 |
| レイアウト | 切り替えの条件（幅だけでなく高さも。例：横向きのスマホ） |
| データ | テーブル、項目、索引、移行、バックアップの形式、CSVなど書き出しの形式 |
| 計算 | 式、境目の扱い、計算例、テストの対象 |
| 外部連携 | 受け渡しの形式、実機での確認結果、失敗したときの戻り方 |
| 公開・更新 | URL、マニフェスト、オフライン、更新の流れ、自動公開の手順 |
| 非機能 | 性能（遅延読み込みなど）、信頼性、セキュリティ、操作性 |

## 5. 具体例（筋トレ記録アプリ：`仕様書/基本設計書.md`）

| 場面 | 起きたこと・決めたこと | 学んだこと |
|---|---|---|
| 画面の切り替え方式 | GitHub Pages では、画面のURLを直接開くと404になる | ハッシュ方式（`#/calendar`）を選び、理由を表に書く |
| 横向きのスマホ | 幅だけで判定すると、横向きのiPhoneがPC向けの配置になる | 「幅768px以上かつ高さ600px以上」を条件にした |
| データ形式の版 | 人体図の部位の廃止（版2）、ステップの追加（版3） | 版ごとの変更を表にし、端末内のデータとバックアップの両方を移行した |
| 計算例 | 「45kcal」と書いたが、実際は45.5を四捨五入して46だった | 計算例は実際に計算し、同じ例を単体テストにする |
| 0時の境目 | 手入力の初期値が、0時直後に「今日の日付＋昨日の時刻」になり保存できなかった | 日付と時刻は同じ時点から作る。境目の扱いを設計に書く |
| ショートカット連携 | JSONで渡すと自動で辞書になり、値がばらばらになった。距離が空欄だと記録に失敗した | 外部への受け渡しは実機で確かめる。うまくいった形式（区切り文字）と、間違えやすい点を設計書に残す |
