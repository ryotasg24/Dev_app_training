# 要件定義書の作成・改訂

「何を作るか」を、開発者でない人が読んでもわかる言葉で決める文書です。
実装方法（どう作るか）は基本設計書（skill：`basic-design-doc`）、見た目はデザイン仕様書（skill：`design-spec-doc`）に書きます。

ひな形：[template.md](template.md)

---

## 1. 進め方（必ずこの順で）

### 手順1：材料を集める
- 既存の要件定義書・メモ・会話の内容を読み、決まっていることと決まっていないことを分ける。
- 既存の文書を改訂する場合は、**必ず先に全体を読み**、版数・変更履歴・未決事項の表を確認する。

### 手順2：作る前に質問する
判断が必要な点は、書き始める前に**まとめて質問**する（1回に4問まで）。
- 各質問に**選択肢を2〜4個**付け、勧める案を先頭に置いて「（推奨）」と書く。
- 選択肢には、選んだ場合に何が起きるか（利点・欠点）を1行で添える。
- 質問は「答えによって書く内容が変わるもの」だけにする。慣例で決められること、資料から確かめられることは質問しない。
- 回答が自由記述で来た場合（計算式の提示など）は、その内容を**そのまま採用**し、式で決まっていない部分だけを自分で補う。補った部分は、報告と文書の両方で「仮定」として明示する。

### 手順3：事実を確認してから決める
推測で書かず、確認できることは確認する。確認できないことは「要確認」として未決事項に入れる。
- **端末・OS・アプリの制約**（例：PWAではヘルスケアに直接書けない、iPhoneのショートカットで選べるワークアウトの種類）は、公式情報か実機で確かめる。ユーザーに実機で確かめてもらった結果は、日付と結果を記録する。
- **外部素材・サービスの利用条件**（ライセンス、再配布の可否）は、利用規約を読んで確かめる。
- **計算式の例**は、実際に計算して確かめる（四捨五入の結果まで）。

### 手順4：書く
[template.md](template.md) の章立てに沿って書く。書き方のルールは「2. 書き方」を守る。

### 手順5：整合を保つ
要件を変えたら、次も同じ作業の中で直す。
- 基本設計書・デザイン仕様書の関連する箇所（要件IDで検索して探す）
- プロジェクトの CLAUDE.md（進み具合、仕様書の版数）
- 版数を上げ、変更履歴に「何を、なぜ」変えたかを1行で書く

### 手順6：報告する
- 変えた箇所を表で示す（箇所・内容）。
- **自分で決めた点（仮定）**を別にまとめ、「変えたい場合は教えてください」と添える。
- 次に決めること・確認してほしいことを最後に書く。

## 2. 書き方

### 文章
- **日本語**で、**平易な言葉**を使う。一文には1つのことだけを書く。
- 専門用語は「用語定義」の章で説明するか、初出でかっこ書きの説明を付ける（例：「PWA（ホーム画面に追加して使うWebアプリ）」）。
- 「〜など」「適切に」のようなあいまいな書き方を避け、数値・条件で書く（例：「起動から3秒以内」「幅768px未満」）。

### 表を中心にする
- 要件・用語・制約・未決事項は、すべて表で書く。
- 要件の表は「ID・要件・優先度」の3列にする。

### 要件ID
- 機能ごとに接頭辞を決め、連番を振る（例：記録 `F-REC-01`、カロリー `F-CAL-01`、データ `F-DATA-01`）。
- **一度振ったIDは変えない・使い回さない**。要件を足すときは、その接頭辞の続きの番号を使う（間に入れたいときも、番号は続きにする）。
- 設計書・コード・コミットメッセージから、IDで参照できるようにする。

### 優先度
| 優先度 | 意味 |
|---|---|
| Must | 最初の版で必須 |
| Should | 最初の版で可能なら入れる |
| Could | 余裕があれば入れる |
| Future | 将来対応。データ構造などの準備だけ先にしておく |

### 未決事項の表
- 列は「No・内容・決める時期」。
- 決まったら行を**消さずに**、内容に取り消し線を引き、「決める時期」の列を「決定済み：○○（参照先）」に書き換える。**番号は振り直さない**（ほかの文書や会話で「未決事項No.1」と呼んでいるため）。

### 決定の記録
- ユーザーと決めたことは、本文に「（2026-11-03 決定）」のように日付を付ける。
- 方針を変えた場合は、変更履歴に理由まで書く（例：「素材に腸腰筋の部位がないため、反り腰の部位を変更」）。

## 3. 必ず検討する観点

書き始める前と、書き終えたあとに、次の観点に漏れがないか確かめる。

| 観点 | 確認すること |
|---|---|
| 目的と範囲 | 誰が、何のために使うか。最初の版でやること・やらないこと（対象外） |
| 端末・環境の制約 | 動かす環境（例：PWA）でできないことと、その代わりの方法 |
| データ | どこに保存するか、消えたらどうなるか、バックアップと復元 |
| 時刻と日付の境目 | 日をまたぐ記録はどの日として数えるか。0時前後で入力や集計が崩れないか |
| 画面サイズ | スマホの縦・横、タブレット、PC。最小の幅（例：320px）で崩れないこと |
| 外部連携 | 連携先で実際に何ができるか（実機で確認）。うまくいかない場合の戻り方 |
| 計算 | 式、使う値、端数の処理、推定値であることの表示 |
| 素材 | 画像・アイコン・図の出典とライセンス（公開してよいか、再配布してよいか） |
| 公開と更新 | 公開先、URL、更新の知らせ方。URLが変わる操作の禁止 |
| 非機能 | 使いやすさ（何タップで始められるか）、性能、オフライン、セキュリティ、保守性 |

## 4. 具体例（筋トレ記録アプリ：`仕様書/要件定義書.md`）

このskillの方針は、次のやり取りから生まれた。新しいアプリでも同じ点に気をつける。

| 場面 | 起きたこと・決めたこと | 学んだこと |
|---|---|---|
| 公開先の確定 | GitHub Pagesでは、URLにリポジトリ名が入る | URLが変わる操作（リポジトリ名の変更）を「制約」に書く |
| 日をまたぐ記録 | 23時〜0時30分の記録をどの日にするか決まっていなかった | 「開始日時の日付で数える」を原則として書く |
| ヘルスケア連携 | 実機で確かめると「筋力トレーニング」「柔軟運動」は選べなかった | 外部の仕様は実機で確かめ、選べる種類（機能的筋力トレーニング等）に合わせて要件を直す |
| たんぱく質の計算 | ユーザーが計算式を提示した | 式はそのまま採用し、式で決まっていない部分（ランニングの係数など）だけを仮定として明示した |
| 記録の流れの変更 | 「押した順にメニューを作り、次の種目へで切り替える」に変更 | 要件を足すときは、IDの続き番号（F-REC-12〜14）を使い、既存IDの意味を変えたものは本文を書き換える |
| 非機能との矛盾 | 「2タップで開始」が、メニュー選択の追加で守れなくなった | 機能を変えたら、非機能要件と矛盾しないか見直す |
